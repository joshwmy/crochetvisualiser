# JSON Schema artefacts

Location: `schemas/*.schema.json` (committed), generated by
`src/crochet_reconstruction/api/schema_export.py`, match-tested by
`tests/test_schema_export.py`.

| `schemas/stitch_graph.schema.json` | `graph.models.StitchGraph` | `GRAPH_SCHEMA_VERSION` |

| `schemas/compile_request.schema.json` | `api.schemas.CompileRequest` | `API_CONTRACT_VERSION` |

| `schemas/diagram_compile_response.schema.json` | `api.diagram_schemas.DiagramCompileResponse` | `API_CONTRACT_VERSION` |

`API_CONTRACT_VERSION` (in `schema_export.py`, currently `"1.0.0"`) is
deliberately a separate version from `GEOMETRY_SCHEMA_VERSION`/
`GRAPH_SCHEMA_VERSION`: the compile API's request/response *shape* (e.g.
adding an optional field to `CompileResponse`) can change on a different
cadence than the geometry/graph payload shapes it happens to embed.

Every schema file also carries a deterministic `$id`
(`https://crochet-reconstruction.invalid/schemas/<filename>` — a symbolic,
never-fetched identifier, not a real published URL) and
`$schema: "https://json-schema.org/draft/2020-12/schema"`.

## Frontend-only types are not included, on purpose

`StitchPathResult` and `Measurement` (`viewer/src/geometry/stitch_paths/types.ts`,
`viewer/src/measurement/types.ts`) do not get a JSON Schema. Both are
computed entirely client-side and never cross the API boundary or get
serialized to JSON at all — see `docs/open-source-resource-adoption.md`'s
JSON Schema re-evaluation. A schema describes a serialization contract
between two independent parties; there isn't one here yet.

## Generating

```
python -m crochet_reconstruction.api.schema_export
```

Writes (or overwrites) every file in `schemas/` from the current Pydantic
models. Deterministic: `sort_keys=True`, no timestamps, no absolute paths,
run twice in a row and the output is byte-identical
(`tests/test_schema_export.py::test_generation_is_reproducible_byte_for_byte`).

**After changing any of the five source models, re-run this command and
commit the result.** `tests/test_schema_export.py` fails the build if the
committed files and the live models disagree — this is what "match-tested"
means in practice: nobody can forget to regenerate, because CI/local test
runs catch it immediately, with an explicit error message naming the exact
command to run.

## Compatibility / version-upgrade behaviour

- **`GeometryDocument.schema_version`** (backend) is checked at load time
  by the frontend: `viewer/src/geometry/load.ts` compares it against
  `SUPPORTED_SCHEMA_VERSION` (`viewer/src/types/geometry.ts`, currently
  `"0.1.0"`) and throws a `GeometryLoadError` — with the received and
  expected versions both in the message — on any mismatch, higher or
  lower. This is an exact-match check, not a semver-range check: there is
  currently exactly one supported version, and the project has never
  needed to reason about partial forward/backward compatibility between
  two different geometry schema versions. Tested in
  `viewer/tests/load.test.ts`.
- **Currently supported version**: `0.1.0` (both `GEOMETRY_SCHEMA_VERSION`
  and the frontend's `SUPPORTED_SCHEMA_VERSION` — kept in sync manually
  today; there is no previously-supported version to compare against,
  since this is the first schema version the project has ever shipped.
- **Unsupported future version behaviour**: rejected with a clear,
  actionable error (`GeometryLoadError`), never silently accepted or
  guessed at. The same exact-match policy applies to a version that is
  *older* than expected, not just newer — the frontend makes no attempt at
  best-effort parsing of an unrecognised shape.
- **`StitchGraph.schema_version`** exists (`GRAPH_SCHEMA_VERSION`) but has
  no equivalent frontend consumer performing a runtime check today — the
  viewer never loads a bare `StitchGraph` on its own (only as embedded data
  inside a `GeometryDocument`-shaped API response, or not at all in the
  structured-JSON-fixture route). Documented here as a gap rather than
  silently assumed handled: if a future feature loads a `StitchGraph`
  independently, it should get the same exact-match version check
  `load.ts` already applies to `GeometryDocument`.
- **`CompileRequest`/`CompileResponse`/`Diagnostic`** have no runtime
  version check at all today — the frontend and backend are always
  deployed together from the same repository (no independent versioning or
  deployment of the two), so a version mismatch between them cannot
  currently occur in practice. This would need to change if the frontend
  and backend were ever deployed independently (e.g. a backend upgrade
  rolled out before the matching frontend build).
- **`API_CONTRACT_VERSION` went `1.0.0` → `1.1.0`** when `options.strict`
  became real behaviour: its default flipped from `true` to `false`, and
  `STRICT_MODE_BLOCKED` joined both diagnostic code enums. Minor rather than
  major because a request that omits `options` — what every current client
  sends, the viewer included — behaves exactly as it did at `1.0.0`. The one
  case that *does* change: a client that explicitly sent `strict: true` while
  the field was a documented no-op now gets strict blocking. That is
  unavoidable in any implementation of the field, and it is the reason the
  default was flipped rather than left at `true`, which would have changed
  behaviour for *every* caller instead of only those who opted in. See
  `docs/compile-api.md`'s "Strict mode".
- **`DiagramDocument`/`DiagramCorrectionSet` and the diagram request/
  response types** have the same "no independent deployment, so no runtime
  check yet" status as the written-pattern API types above — same gap,
  same reasoning, not yet a problem in practice. `DIAGRAM_SCHEMA_VERSION`
  (currently `"1.0.0"`) and `CORRECTIONS_SCHEMA_VERSION` (currently
  `"1.0.0"`) are independent of `GRAPH_SCHEMA_VERSION`/
  `GEOMETRY_SCHEMA_VERSION` for the same reason `API_CONTRACT_VERSION` is
  independent of them: a diagram-specific shape change (e.g. a new
  `DiagramSymbol` field) can happen on a different cadence than the
  `StitchGraph`/`GeometryDocument` payloads a compiled diagram still
  ultimately embeds unchanged.
