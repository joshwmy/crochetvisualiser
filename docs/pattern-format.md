# Pattern format

The structured `Pattern` object (`domain/pattern.Pattern`) is the single
source of truth. Nothing else — not the rendered text, not any future API
response — is authoritative over it.

## Shape

```
Pattern
├── schema_version: str                 # "0.1.0"
├── input: ProjectInput                 # validated user input, echoed back
│   ├── project: ProjectMetadata
│   ├── terminology: Terminology        # "US" (only supported value)
│   ├── template: TemplateRef           # {id, version}
│   ├── measurements: UserMeasurements
│   ├── gauge: Gauge
│   ├── negative_ease_pct: Decimal
│   ├── construction: Construction
│   ├── brim_type: BrimType
│   ├── yarn: YarnMetadata | None
│   └── hook: HookMetadata | None
├── calculated: CalculatedParameters    # every derived numeric value
├── assumptions: list[Assumption]       # provenance-tagged facts/choices
├── components: list[Component]         # crown, body, [brim] — in order
│   └── rounds: list[Round]
│       └── operations: list[Operation] # tagged union, see below
├── validation: ValidationReport | None # None only before compilation completes
└── fingerprint: str | None             # sha256 over canonical JSON, sans this field
```

## Operations (tagged union, `domain/operations.py`)

`magic_ring`, `stitch`, `increase`, `decrease`, `repeat`. Each has explicit
consumed/produced semantics via `consumed_count()` / `produced_count()` —
there is exactly one place in the codebase that knows how to compute these,
and both the compiler and the validator call it (no duplicated arithmetic).
`decrease` is modelled but never generated by a Phase 1 template.

## Canonical serialisation and fingerprint

`engine.compiler.canonical_json(pattern)` produces a key-sorted,
whitespace-minimal JSON string of the pattern (via
`pattern.model_dump(mode="json")`, which converts `Decimal` and enum values
to their JSON string forms), **excluding the `fingerprint` field itself**.
The fingerprint is `sha256(canonical_json(pattern).encode("utf-8")).hexdigest()`.

**Guarantee:** identical `ProjectInput` values always produce identical
`Pattern` content and therefore identical fingerprints — verified by both a
unit test (`tests/unit/test_compiler.py`) and a Hypothesis property test
(`tests/property/test_engine_properties.py`) across the template's
supported input range.

## Versioning strategy

- `Pattern.schema_version` (currently `"0.1.0"`) versions the *shape* of the
  structured representation. A minor version may add optional fields; a
  major version may change semantics of existing fields.
- `TemplateRef.version` (currently `"1.0.0"` for `top_down_basic`) versions
  the *template's* rules independently of the schema — e.g. widening the
  allowed crown increase schedule set is a template version bump, not a
  schema version bump.
- `ValidationReport.engine_version` records which compiler/validator code
  produced the report, independent of both of the above.
- Patterns are never mutated in place. Regenerating from changed
  measurements/gauge produces a new `Pattern` value (Phase 1 has no
  persistence layer, so "new value" currently just means "a new Python
  object" / a new CLI output directory — a future phase adding storage
  would assign a new immutable version identifier here rather than
  overwriting).

## What renders the pattern is not the source of truth

`rendering/text_renderer.render_text` reads `Pattern` fields directly and
performs no arithmetic. It is a one-way view. Nothing parses the rendered
text back into structured data anywhere in this codebase — a change to
wording can never silently change what the pattern "is."
